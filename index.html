01 / PROBLEM

A successful import was only the start.

In jewellery, a difference of 0.001 matters. Moving records was insufficient: amounts, weights, charges and customer details had to remain consistent across every module so cash books, bank books, stock and opening and closing balances would tally.

The source kept changing. Around 1,000 new vouchers were created each business day across the branches and head office, adding a daily migration workload alongside the historical transfer.

02 / APPROACH

Code the migration. Reconcile the business.

I built the migration in C#/.NET, with substantial SQL Server work for source mapping, data investigation and reconciliation. Validation, failure logging, rollback and retries were part of the migration process.

Checks covered both individual vouchers and their effect across 17+ modules. The acceptance criterion was agreement with the business records, including that day’s closing and the next day’s opening.

03 / HARD FAILURE

The first checks exposed mismatches.

Initial validation caught and logged discrepancies. I traced some to source-data inconsistencies; others required additional checks using the jewellery business’s calculation rules.

I investigated the mismatches, addressed the inconsistencies and added calculation-based validation before retrying and reconciling the affected data. Completing a transfer could not substitute for proving that the figures matched.

04 / DELIVERY CONSTRAINT

Finish between closing and opening.

I used Hyper-V virtual machines to run branch migrations in parallel overnight. Once trading stopped, the day’s database backups provided the source for migrating the latest business data alongside the historical records.

This created a defined window for migration, validation, rollback and retries. Verification was completed before the client’s next business day, under the go-live deadline.
